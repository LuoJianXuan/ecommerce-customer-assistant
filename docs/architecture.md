# 架构与工程边界

## 主对话链路

入口为 `POST /api/agent/chat`，前端使用 SSE（服务器发送事件）接收状态与回复。状态检查点使用 SQLite（轻量数据库）保存。

`app/agent/graph.py` 的 `INTENT_ROUTE` 包含 8 类意图，`ROUTE_TARGET` 有 5 个目标：

| 意图 | 路由键 | 首个目标 | 后续行为 |
| --- | --- | --- | --- |
| 商品咨询 | knowledge（知识） | retrieve（检索） | 检索 → 证据闸 → 智能体或保守答复 |
| 退款退货、售后 | aftersale（售后） | aftersale_orders（售后订单） | 查单/选择订单 → 政策检索 → 智能体 |
| 订单、物流、其他 | agent（智能体） | agent | 按需调用工具，可追问澄清 |
| 投诉 | complaint（投诉） | complaint | 固定安抚与人工处理建议 |
| 闲聊 | chat（闲聊） | chat | 固定回复 |

无法识别的意图默认走知识路径。知识分支的证据闸不是所有分支共同经过的节点；投诉与闲聊的固定答复也不意味着整轮没有意图识别模型调用。

## 知识和检索

MySQL 保存知识原文及治理状态；Milvus 保存稠密向量、文本和关键词检索索引。只有 active（可检索）知识进入正常召回。

两路各召回 50 条，通过 RRF（倒数排名融合）合并。公开模板取前 6 条重排，`RERANK_TOP_K=10` 是返回上限，不表示一定产生 10 条结果。应用配置类保留候选默认值 20，因此复现时应显式加载模板或当次配置，不能仅引用类默认值。

向量化采用 pending（待完成）状态与确定性向量主键。成功 upsert（插入或更新）后再回填 MySQL；失败留下待补齐项，可通过 `python -m app.knowledge.build --resume` 继续。

## 工具和上下文

- 工具区分只读与写入。只读支持超时重试；写入需确认，不自动重试，避免超时后重复执行。
- 订单来自本地表及演示播种，商品为演示目录，物流与优惠工具提供模拟数据；未对接真实企业业务系统。
- 近期原文、工具结果及早期摘要分层使用预算。摘要异步完成前仍使用原锚点，不宣称存在未经对照实验验证的“信息保留率提升 50%”。
- 主题分类属于离线旁路；实时业务意图识别与 17 类多标签分类不是同一模型。

## 已知边界

- 当前主链路终答在智能体聚合后按 3 字分片发送，属于 SSE 分段展示，不是模型词元的端到端转发。
- 审核发布先提交知识和“已通过”状态，再向量化；向量化失败没有自动回滚审核状态，需要补齐。不能表述为“向量化成功才审核通过”。
- 示例知识存在部分口径重叠或冲突，冻结评估只记录，没有擅自统一会员、保修、退货时效等业务规则。
- 检索与生成审计、证据闸诊断、工作流端到端回归分别验证不同内容，不能互相替代成功率。
- 当前为本地作品与验证环境，没有以生产权限、并发、可用性或真实业务收益为验收目标。公开仓库不附真实用户数据、运行配置与模型权重。
